# Оверхед схемы «устройство вне процесса через vfio-user-pci» против нативного устройства QEMU

Дата: 2026-11-07. Стенд: AMD Threadripper PRO 5975WX, LXC на хосте с ядром 7.0.14-pve, стоковый QEMU v11.1.3
(собран из upstream-тега, без патчей), libvfio-user master, kvm-unit-tests master. 1 vCPU, без привязки к ядрам.
Методика, исходники и сырые результаты: `bench/` (см. `bench/README.md`). Тики TSC переведены в мкс по 3593 МГц.

## 1. Главный вывод

Оверхед не «размазан» по всему устройству, а сосредоточен в трёх путях. Для каждого есть либо
нулевой оверхед, либо кратный, в зависимости от того, как спроектировано устройство и как запущена VM.

| Путь | Нативное устройство | vfio-user (стоковый клиент QEMU 11.1) | Разница |
|---|---:|---:|---|
| MMIO-запись в регистр (doorbell), posted | 3.1 мкс | 4.8–5.0 мкс | +1.7 мкс, ×1.55 |
| MMIO-чтение регистра | 3.3 мкс | 22–26 мкс | ×7–8 |
| PIO-запись / PIO-чтение | 2.6 мкс | 22–26 мкс | ×9–10 (PIO-записи не posted) |
| MMIO-запись при наличии mmap-региона или с `x-no-posted-writes` | 3.1 мкс | 23–24 мкс | ×7.5 |
| Doorbell через ioeventfd (только ядро) | 1.4 мкс | нет в клиенте | нет |
| Обращение к BAR, отображённому в память (RAM-BAR / mmap-BAR) | ~1 нс, без выхода | ~1 нс, без выхода | 0 |
| DMA 4 КиБ, память гостя общая (memfd share=on) | memcpy в процессе | 1.0–1.1 мкс (mmap + memcpy) | ≈0 |
| DMA 4 КиБ, память гостя не общая (сообщения DMA_READ) | memcpy в процессе | 20–27 мкс на запрос | ×20 и выше |
| DMA 64 КиБ через сообщения | | 33–43 мкс | |
| MSI-X | irqfd | тот же irqfd, eventfd передан серверу | ≈0 (по коду, не измерялось) |

Вывод для проектирования: если устройство сделано «современно» (doorbell = posted-запись, очереди и
статус в памяти гостя через DMA, завершения через MSI-X), а память гостя общая, то измеримый оверхед
на одну операцию ввода-вывода составляет около +1.7 мкс на doorbell и ничего больше. Если устройство
«старое» (чтение регистров состояния в горячем пути, PIO, DMA без общей памяти), каждая такая операция
стоит 20–27 мкс вместо 3, то есть в 7–10 раз дороже.

## 2. Откуда берутся цифры (по исходникам клиента hw/vfio-user в QEMU 11.1)

- Запись в memory-BAR отправляется как `VFIO_USER_REGION_WRITE` с флагом NO_REPLY (posted), поток vCPU
  делает только `sendmsg` и продолжает выполнение (`hw/vfio-user/device.c`, `vfio_user_device_io_region_write`).
  Отсюда +1.7 мкс. Клиент также умеет склеивать posted-записи в `WRITE_MULTI`, когда очередь переполнена.
- Чтение и PIO-запись синхронны: vCPU шлёт запрос и ждёт на условной переменной (`proxy.c`,
  `vfio_user_send_wait`); ответ принимает отдельный iothread `vfio-user` (`proxy.c:961-964`), который будит
  vCPU. Итого три межпоточных/межпроцессных пробуждения: vCPU→сервер, сервер→iothread, iothread→vCPU.
  На этом хосте это 20–26 мкс. Polling-сервер (без блокирующего recv) убирает одно пробуждение:
  измерено 18–20 мкс вместо 22–26.
- Если хоть один регион устройства объявлен mmap-able, клиент отключает posted-записи для всего
  устройства, чтобы сохранить порядок записей и чтений (`device.c:200-210`). Измерено: запись в
  обычный BAR при наличии mmap-BAR2 стала 23 мкс вместо 4.8.
- `VFIO_USER_DEVICE_GET_REGION_IO_FDS` (ioeventfd/ioregionfd для doorbell) описан в протоколе, но в
  клиенте QEMU 11.1 не реализован (в `hw/vfio-user/` нет ни одного обращения). Поэтому doorbell быстрее
  posted-записи (4.8 мкс) в стоковом QEMU не сделать. Для сравнения: ioeventfd у нативного устройства 1.4 мкс.
- DMA: клиент передаёт серверу fd памяти гостя только если у region есть fd (`container.c`,
  `memory_region_get_fd`), то есть при `memory-backend-memfd`/`-file` с `share=on`. Без fd сервер вынужден
  слать `VFIO_USER_DMA_READ/WRITE`, которые QEMU обрабатывает в main loop под BQL
  (`hw/vfio-user/pci.c:194`), максимум 1 МиБ на сообщение (`VFIO_USER_DEF_MAX_XFER`).
- Взаимоблокировка: если сервер делает DMA через сообщения внутри обработчика синхронного доступа
  (чтение или PIO), vCPU держит BQL в ожидании ответа, а обработчик DMA_READ ждёт BQL. Измерено: обе
  стороны отваливаются по таймауту 5 с (`x-msg-timeout`). Это не баг стенда, а свойство стокового клиента.
- Пограничный случай: запрос DMA_READ ровно в 1 МиБ (равен `max_data_xfer_size`) обрывает соединение
  (libvfio-user + QEMU 11.1.3). Делить передачи на куски меньше лимита.
- MSI-X: общий код `hw/vfio/pci.c` создаёт eventfd и регистрирует его как KVM irqfd
  (`vfio_add_kvm_msi_virq`), серверу через `SET_IRQS` уходит именно этот fd. Сервер пишет в eventfd, KVM
  инжектирует прерывание без участия QEMU. Путь тот же, что у VFIO passthrough и vhost-user.

QEMU в роли сервера (`x-vfio-user-server` + тот же `pci-testdev`) даёт ту же картину: posted-запись 5.5 мкс,
чтение 24.6 мкс, PIO 23.8 мкс. То есть цена определяется клиентом и протоколом, а не реализацией сервера.

## 3. Как уменьшить оверхед (по Парето: сначала самое дешёвое и самое весомое)

1. Общая память гостя. `-object memory-backend-memfd,id=m0,size=...,share=on -machine memory-backend=m0`
   (лучше с hugepages и prealloc). Это убирает ×20 на DMA и класс взаимоблокировок. Без этого схему для
   устройств с DMA запускать нельзя. В PVE общая память включается вместе с hugepages или virtiofs,
   проверить итоговую командную строку `qm showcmd`.
2. Горячий путь без синхронных обращений. Doorbell = posted MMIO-запись; никаких чтений регистров и PIO в
   горячем пути; статус, очереди, завершения в памяти гостя (DMA) плюс MSI-X. Это превращает ×7–10 в +1.7 мкс.
3. Все BAR только через сообщения, без mmap-регионов, пока doorbell идёт через сообщения. Иначе клиент
   отключает posted-записи и doorbell дорожает до 23 мкс. Если очень нужен регион с прямым доступом,
   положить его в память гостя (DMA в общей памяти), а не в BAR.
4. Сервер: отдельный поток на сокет с busy-poll (`LIBVFIO_USER_FLAG_ATTACH_NB`, `vfu_run_ctx` в цикле)
   даёт −15–20% на синхронных операциях; DMA и тяжёлую работу выносить в рабочие потоки, никогда не
   делать IPC-DMA внутри обработчика доступа.
5. Меньше doorbell на единицу работы: глубокие очереди, батчинг, interrupt coalescing. Клиент сам склеивает
   posted-записи в `WRITE_MULTI` при заторе, но лучше не доводить до затора.
6. Без vIOMMU для этой VM (или passthrough-режим): иначе каждое изменение отображений превращается в
   DMA_MAP/UNMAP-сообщения. Не измерялось, следует из механизма.
7. Для virtio-класса устройств использовать vhost-user, а не vfio-user: там doorbell идёт через ioeventfd
   (1.4 мкс по нативному замеру), а не через posted-запись (4.8 мкс).
8. Не доступно в стоковом QEMU: ioeventfd/ioregionfd/shadow ioeventfd для vfio-user. На KVM Forum 2025 для
   shadow ioeventfd заявлены выигрыши до 200% по задержке и CPU, но нужны патчи ядра и QEMU, что
   противоречит требованию «стоковый QEMU». Отслеживать появление `GET_REGION_IO_FDS` в клиенте.

## 4. Что это значит для throughput-устройств

Опубликованные данные Intel/SPDK (KVM Forum 2021, слайды): fio в VM, 4K random read, QD128: vfio-user NVMe
725K IOPS, vhost-user-blk 786K IOPS, физический диск 860K IOPS, spdk perf внутри VM через vfio-user 853K.
То есть при общей памяти и очередях с doorbell схема «вне процесса» держит около 84–99% от железа и на
уровне vhost-user. Это согласуется с замером: на одну операцию остаётся только +1.7 мкс на doorbell.

## 5. Ограничения замера

- Один хост, один vCPU, без привязки к ядрам, разброс между прогонами синхронных операций до ±15%.
- Базовая стоимость выхода из гостя на этом хосте высокая (vmcall 2.3 мкс), абсолютные цифры на PVE-хосте
  могут отличаться; относительные соотношения определяются числом пробуждений и переносимы.
- Задержка прерываний не измерялась, оценка по коду.
- libvfio-user master на 2026-11-07, QEMU v11.1.3; клиент в PVE 11.1.3 тот же код.
